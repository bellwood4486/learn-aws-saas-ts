    CHAPTER 0infra/ 全体

    全体像：なぜ 6 層に分けるのか

    infra/ には Terraform の「root module」が 6 つ並んでいます。AWS のサービス別ではなく、コストとライフサイクルで切った 6 つです。この教科書は、その切り方の理由と、各層のコードに込められた判断を順に読み解きます。まずは全体の地図から。

    この章で読み解くこと

    • 「月 $10」という制約が、Terraform の分割方針をどう決めたか
    • 6 つの層それぞれの役割・ライフサイクル・コスト
    • POST /api/items 1 本が、どのリソースをどう通るか

    設計を支配する制約：月 $10

    教科書どおりの「本番構成」を素直に立てて常時起動しておくと、AWS の月額はこうなります。学習価値のほとんどない「配管」だけで予算を大きく超えてしまいます。

    常時起動した場合月額目安
    NAT Gateway ×1約 $35〜40
    ALB約 $18〜22
    RDS db.t4g.micro約 $12〜15
    Fargate 0.25vCPU / 0.5GB ×2約 $20〜30
    DynamoDB / SQS / S3 / ECR / Secrets Manager / Cognito / CloudFront約 $2（ほぼゼロ）

    高いのは NAT・ALB・RDS・Fargate の 4 つで、しかも「使っていない時間」に課金され続けます。一方、最終行のサービス群は放置してもほとんど課金されません。この性質の違いが、分割の軸になります。

    設計判断

    Terraform を「サービス別」ではなく「ライフサイクル別」に分け、高コストな層は触るときだけ apply して、終わったら destroy する。どの層が高コストか、どの層がステートフルかを意識して境界を切ること自体が、この構成の学習成果になっています。

    6 つの層

    層中身ライフサイクルコスト
    bootstraptfstate 用 S3 バケット一度だけ約 $0
    platformアプリ用 S3・DynamoDB・SQS+DLQ・ECR・Secrets・Cognito・GitHub OIDC と CI/CD ロール常時起動約 $1/月
    edgeフロント用 S3・CloudFront（2 オリジン）・deploy-web ロール常時起動約 $0（時間課金なし）
    networkVPC・subnet ×2AZ・IGW・NAT・route table・SGセッション毎NAT $0.062/h + EIP $0.005/h
    dataRDS・DB 認証情報のシークレット・SSM 踏み台セッション毎（唯一のステートフル）RDS 約 $0.02/h
    appALB・ECS クラスタ・タスク定義・サービス ×2・Logs・IAM ロールセッション毎ALB $0.024/h + Fargate

    常時起動の 2 層（platform / edge）は月 $2 前後。セッション毎の 3 層（network / data / app）は 1 セッション（4 時間）で約 $0.6。月 10 回使っても $8 前後に収まる計算です。

    設計判断

    CloudFront を 2 オリジンにするのが要。既定のパスは S3（SPA）、/api/* は ALB に流します。独自ドメインが無くても *.cloudfront.net の証明書で HTTPS になり、次の 3 つが同時に片付きます。

    1. mixed content：HTTPS のページから HTTP の ALB は呼べない。CloudFront が HTTPS を終端し、CloudFront → ALB は HTTP でよい
    2. CORS：フロントと API が同一オリジンに見えるので、CORS 設定が要らない
    3. Cognito：localhost 以外では HTTPS が必要になる

    この教科書の読み方

    各章は「その層が解く問題 → 実コードの読解 → 設計判断 → クイズ」の順です。コードの色付きの行や番号バッジをクリックすると、その行の「何をしている？／なぜこう書く？／外す・間違えると？」が出ます。クイズは選択式で、答えるとすぐ解説が出ます。章は依存順（apply する順）に並んでいるので、上から読むのがおすすめです。

    手元で、各層が単独で plan できることを確かめてみましょう。plan は何も作らないので課金は発生しません（AWS の認証は済んでいる前提）。

    just tf-plan platform

    確認クイズ

    Terraform の root module を 6 つに分けた、最大の理由はどれでしょう？
    1. 高コストな層だけを「触るときだけ apply、終わったら destroy」できるよう、コストとライフサイクルで境界を切るため
    2. AWS のサービスごとに root module を分けるのが Terraform の公式推奨だから
    3. dev / stg / prod の 3 環境を、それぞれ別の root module で管理するため
    4. tfstate が大きくなると apply が極端に遅くなるのを避けるため

    この構成の環境は dev 単一なので、環境別の分割ではありません。分割の軸は「コスト」と「ライフサイクル」です。NAT・ALB・RDS・Fargate だけを毎回作って消し、S3 や DynamoDB のような安いものは常時起動のままにする。これを 1 つの root module でやろうとすると、-target だらけになってしまいます。

    セッション終了時に just down で層を destroy すると、「データが失われる」のはどの層でしょう？
    1. data（RDS が消える）
    2. network（VPC・NAT が消える）
    3. app（ALB・ECS が消える）
    4. edge（フロントの S3・CloudFront が消える）

    ステートフルなのは data 層の RDS だけです（踏み台 EC2 はステートレス）。学習用途なので「消えるのを受け入れる」代わりに、スキーマは Drizzle の migration（just db-migrate）、初期データは seed で毎回流し直します。なお edge は常時起動層なので just down では destroy されません（再 apply されるだけです。詳しくは第 6 章）。

    CloudFront を、セッション毎の app 層ではなく常時起動の edge 層に置いています。現在のコードで今も成り立っている根拠はどれでしょう？
    1. distribution の destroy は「disable → 伝播待ち → 削除」と遅く、しかも時間課金がないので、消す金銭的な意味がないから
    2. CloudFront は時間課金が高く、常時起動のほうが割安になるから
    3. distribution を作り直すたびに *.cloudfront.net のドメインが変わり、Cognito のコールバック URL を毎回書き換える必要があるから
    4. CloudFront は VPC の外にあるので、app 層（VPC 内）とは同じ root module に置けないから

    3 番目は当初の設計理由でしたが、実装で認証方式を「直接ログイン（USER_PASSWORD_AUTH）」にしたため、コールバック URL 自体を使わなくなり、根拠として消えました。今も残っているのは 1 番目です。設計の理由は実装とともに変わりうる、という好例です。

    CloudFront を 2 オリジンにして「同一オリジン」に見せると、いくつかの問題が片付きます。これでは解決しないものはどれでしょう？
    1. HTTPS のページから HTTP の ALB を呼べない（mixed content）
    2. ブラウザからの API 呼び出しに CORS 設定が要る
    3. Cognito が localhost 以外で HTTPS を要求する
    4. ALB の DNS 名がセッション毎に変わる

    ALB は app 層で毎回作り直されるので、DNS 名は毎回変わります。2 オリジン構成でも、CloudFront の /api/* の向き先（オリジン）は誰かが更新しなければなりません。これを Terraform の dynamic ブロックと「再 apply」で解いているのが第 6 章のハイライトです。

    CHAPTER 1bootstrap一度だけ apply

    bootstrap：state を置く場所を先に作る

    Terraform は「今どのリソースを管理しているか」を tfstate というファイルに記録します。この構成では、全 6 層の tfstate を 1 つの S3 バケットに置きます。そのバケットを作るのが bootstrap 層で、すべての層の出発点です。

    この章で読み解くこと

    • 「state の置き場所を、state で管理できない」というニワトリと卵の問題の解き方
    • S3 backend の設定（key / use_lockfile）と、バケット名を -backend-config で渡す理由
    • state バケットに付ける 4 つの守り（versioning・暗号化・公開ブロック・prevent_destroy）

    ニワトリと卵の問題

    S3 backend を使うには、先にバケットが存在していなければなりません。でもそのバケットを Terraform で作るなら、その state はどこに置くのか。答えは「この層だけ local state（手元のファイル）を使い、そのファイルをリポジトリに commit する」です。

    1. ① bootstraplocal state で apply → バケットができる
    2. →
    3. ② 他の 5 層そのバケットを S3 backend として使う

    bootstrap の tfstate には S3 バケット関連のリソース情報しか入りません（DB パスワードのような秘匿値を持たない層なので、commit しても許容できます）。

    コードを読む①：state バケット本体

    コードを読む②：バケットに付ける守り

    S3 バケットの設定は、AWS provider v4 以降、バケット本体とは別のリソースに分かれています。「1 バケット = 5 リソース」は、この provider の作りに由来する書き方です。

    コードを読む③：他の層は、どうやってこのバケットを使う？

    例として platform 層の providers.tf を読みます。他の層（network / data / app / edge）も、key と Layer タグ以外は同じ形です。

    バケット名はどう渡される？

    渡しているのは justfile のレシピです。bootstrap の output からバケット名を取り出して -backend-config に渡します。

    やってみよう（課金なし）

    backend が本当に S3 を向いているか、state の中身を一覧してみましょう。

    cd infra/platform && terraform state list

    bootstrap 側で同じことをすると、リソースが手元のファイルから読まれます。

    確認クイズ

    bootstrap 層だけが local state を使っています。なぜでしょう？
    1. state 用の S3 バケットは bootstrap 自身が作るので、そのバケットを bootstrap の backend にはできないから
    2. S3 backend は、1 つの root module にしか設定できないから
    3. local state のほうが、S3 より安全だから
    4. bootstrap は一度も apply しないので、state が不要だから

    バケットを作る Terraform の state を、まだ無いそのバケットに置くことはできません。そこで bootstrap だけ local state で作り、そのファイルを commit して保管します。他の層はすべて、このバケットを backend にします。

    各層の backend "s3" に bucket = "..." が書かれていません。どうしてでしょう？
    1. bucket は省略可能で、省略するとデフォルトのバケットが使われるから
    2. backend ブロックでは変数や data source が使えず、アカウント ID を含むバケット名を直書きしないために、-backend-config で渡すから
    3. バケットの指定は provider "aws" ブロックにあるから
    4. bucket は required_providers で宣言するから

    just tf-plan などのレシピが、bootstrap の output tfstate_bucket を -backend-config="bucket=..." で渡します。このやり方を partial configuration と呼びます。data 層の data.tf にも、「backend 側は -backend-config で受け取るが data source には渡らないため、バケット名を同じ規則で組み立てる」というコメントがあります（第 4 章）。

    bootstrap で、何も変更しないまま terraform destroy を実行すると、どうなるでしょう？
    1. 確認プロンプトの後、バケットが削除される
    2. バケットが空なら削除され、中身があれば失敗する
    3. state ファイルだけが消えて、バケット自体は残る
    4. prevent_destroy のエラーで、plan の段階で止まる

    prevent_destroy = true が付いたリソースを destroy する計画は、実行前にエラーになります。本当に作り直したいときは、コメントにあるとおり lifecycle ブロックを一時的に外します。「壊したくないものは、コードで壊せなくしておく」という考え方です。

    use_lockfile = true は何のための設定でしょう？
    1. tfstate ファイルを暗号化するため
    2. 同時に apply が走ったとき、後から来た側をエラーで止めて state の破損を防ぐため
    3. state の古い版を自動的に削除するため
    4. DynamoDB のロックテーブルを自動で作るため

    S3 のネイティブなロックです。従来必要だった DynamoDB のロックテーブル（dynamodb_table）は deprecated で、将来削除されるので、この構成では作りません。暗号化は bootstrap のバケット側の設定（SSE-S3）が担当します。

    state バケットのバージョニングを有効にしている、いちばんの目的はどれでしょう？
    1. state のダウンロードを速くするため
    2. 他の層からも、同じ state を共有できるようにするため
    3. state が壊れたり誤って上書きされたりしたとき、過去の版に戻せるようにするため
    4. 暗号化の強度を上げるため

    tfstate を失うと、Terraform は実在するリソースを「知らないもの」として扱ってしまいます。バージョニングは、そのときの復旧手段です。共有は S3 backend 自体の機能、暗号化は SSE の設定で、それぞれ別の話です。

    CHAPTER 2platform常時起動

    platform：常時起動の土台

    DynamoDB・SQS・ECR・Secrets Manager・Cognito・アプリ用 S3、それに CI/CD 用の GitHub OIDC。放置しても月 $1 程度で済み、消す意味がないものを集めた層です。セッション毎の層（network / data / app）は、これらを「あるもの」として使います。

    この章で読み解くこと

    • SQS と DLQ、ECR の IMMUTABLE とライフサイクルルールの、設計の意図
    • Secrets Manager の recovery_window_in_days と ignore_changes
    • GitHub Actions が、アクセスキーなしで AWS に入る仕組み（OIDC の信頼ポリシー）

    なぜここに置く？

    platform に置いたものには共通点があります。1 リクエスト分の課金がほぼゼロ（DynamoDB のオンデマンド、SQS、S3、ECR、Cognito）か、置いても月数十セント（Secrets Manager は 1 本 $0.40/月）で、しかもセッションをまたいで残したいものばかりです。たとえば ECR のイメージは、app 層を壊しても残っていないと、次のセッションで毎回ビルドし直しです。

    コードを読む①：DynamoDB と SQS

    コードを読む②：ECR（イメージ置き場）

    コードを読む③：Secrets Manager と Cognito

    コードを読む④：GitHub Actions が、アクセスキーなしで入る仕組み

    CI/CD に IAM ユーザーのアクセスキーを渡すと、それが漏れた瞬間に終わりです。代わりに OIDC（OpenID Connect）を使います。GitHub Actions が実行時に「私は、このリポジトリの main ブランチで動いている workflow です」という署名付きトークンを出し、AWS が「その条件なら、このロールを貸す」と判断します。長期に有効な鍵はどこにも保存されません。

    次は deploy-api ロールの権限です。最小権限は「対象を明示できるところは明示する」ことです。ただし、AWS の仕様上、明示できない操作もあります。

    設計判断

    このロール（github_deploy_api）は、なぜ app 層ではなく platform 層に置くのでしょう。app 層は毎セッション destroy されます。ロールが app 層にあると、CI の設定（GitHub Variables に登録したロール ARN）を毎回作り直すことになります。権限を受け取る側が消えても、ロール自体は常時存在させたいので、常時起動層に置いています。これは第 7 章の「CI/CD の粒度がライフサイクルに従う」につながります。

    確認クイズ

    ECR は IMMUTABLE です。ローカルから、すでに存在する abc1234 というタグに、内容を変えたイメージを docker push するとどうなるでしょう？
    1. 古いイメージが、新しいイメージで上書きされる
    2. 2 つのイメージが、同じタグで並んで残る
    3. push が失敗する
    4. 古いイメージが自動で削除され、新しいものが残る

    IMMUTABLE では、既存のタグへの上書きが拒否されます。だからこの構成は latest を使わず、7 桁の commit SHA でタグ付けします。「タグ＝コミット」なので、動いているコードの特定もロールバックも簡単です。ECR が IMMUTABLE なので、CI（publish-image）も同じタグが既にあれば push を飛ばします。

    ECR のライフサイクルポリシー（最新 10 個だけ保持）を入れ忘れると、何が起きるでしょう？
    1. ECR への push が、できなくなる
    2. イメージのスキャンが、動かなくなる
    3. main のコミットごとに 200〜300MB のイメージが溜まり続け、ストレージ課金が月 $10 の予算を圧迫する
    4. 古いタグが自動で上書きされ、ロールバックできなくなる

    ECR のストレージは $0.10/GB・月です。数十イメージ溜まると、予算の無視できない割合になります。このポリシーは衛生のためではなく、予算のための設定です。ただし代償として、セッション中に main へ 10 コミット以上入ると、稼働中のタグが消える可能性があります。

    platform の aws_secretsmanager_secret_version.app には ignore_changes = [secret_string] があります。この設定が必要な理由はどれでしょう？
    1. secret_string が大きすぎて、差分の計算が遅くなるから
    2. Secrets Manager が、値の更新を Terraform 経由では受け付けないから
    3. 実キーは CLI やコンソールで投入する運用で、無いと次の apply でダミー値（REPLACE_ME）に巻き戻ってしまうから
    4. recovery_window が 0 のとき、必ず必要になる設定だから

    Terraform が「値の持ち主でない」（外から値を入れる運用の）シークレットには、ignore_changes を付けます。data 層の DB シークレットは反対に、Terraform が random_password で値を作る持ち主なので、付けません（第 4 章）。

    feature ブランチ上の workflow が、github_deploy_api ロールを assume しようとします。何が起きるでしょう？
    1. ロールを assume できて、ECS を更新できる
    2. assume はできるが、ECS の更新だけが拒否される
    3. 信頼ポリシーの sub 条件（main ブランチのみ）に合わず、AssumeRoleWithWebIdentity が拒否される
    4. GitHub 側の設定で、workflow 自体が起動しない

    ロールの信頼ポリシーが、sub を ...:ref:refs/heads/main に固定しています。assume そのものが拒否されるので、権限を見に行く前に止まります。deploy-api の workflow が最初のステップで「main から実行しているか」を確認するのは、この失敗を「分かりやすいエラー」にするためです。

    あるメッセージの処理（processItem）が、毎回例外で失敗します。worker は例外を握りつぶしてログを出すだけで、メッセージを削除しません。どうなるでしょう？
    1. worker が、無限ループで同じメッセージを処理し続ける
    2. 1 回失敗した時点で、メッセージが DLQ に移される
    3. 30 秒後に再配信され、3 回受信しても削除されなければ DLQ に移される
    4. SQS がメッセージを自動で削除し、失敗は記録に残らない

    worker は「失敗したら削除しない」だけで、再試行の制御を SQS（可視性タイムアウト 30 秒＋ maxReceiveCount = 3）に任せています。DLQ に移った後も、DynamoDB の status は pending のままです（failed という状態は作っていません）。

    iam:PassRole の対象を role/${var.project_name}-* のようなワイルドカードにしていません。その理由はどれでしょう？
    1. ワイルドカードは、IAM ポリシーの resources に書けないから
    2. ワイルドカードだと、ロールがまだ存在しないとき plan が失敗するから
    3. github_publish など CI 用ロール自身にもマッチしてしまい、権限昇格に使われうるから
    4. ワイルドカードは、apply のたびに差分を生むから

    ロール名が <プロジェクト名>-github-... で始まるものにもマッチしてしまうからです。PassRole は「そのロールを別サービスに使わせる」権限なので、対象を絞らないと、意図しないロールを渡せてしまいます。なお、IAM ポリシーには存在しないロールの ARN も書けるので、app 層が destroy 済みでも問題ありません。

    Cognito の App Client で generate_secret = false にしています。理由はどれでしょう？
    1. シークレットを発行すると、Cognito の料金が上がるから
    2. ブラウザで動く SPA はシークレットを隠せないので、シークレットの無い「パブリッククライアント」にするから
    3. シークレットを使うと、JWT の検証ができなくなるから
    4. USER_PASSWORD_AUTH は、シークレットがあると使えないから

    SPA のコードはユーザーのブラウザに配られるので、そこに埋めたシークレットは誰でも読めます。だから「持たないクライアント」にして、ユーザー名とパスワードで直接ログインする方式にしています。

    CHAPTER 3networkセッション毎

    network：VPC とセキュリティグループ

    VPC・2AZ の subnet・NAT Gateway・route table、そして ALB / ECS / RDS / 踏み台の SG（セキュリティグループ）。教科書どおりの private subnet + NAT 構成を、コストの高い部分だけセッション毎に作り直します。

    この章で読み解くこと

    • public / private subnet と、NAT Gateway が要る理由
    • SG を「1 ルール = 1 リソース」で書く attachment パターン
    • この層には「箱（SG）」だけがあり、中身（ALB・ECS・RDS 本体）は後の層にある設計

    コードを読む①：VPC と subnet

    コードを読む②：NAT Gateway と route table

    private subnet のリソースは、外から到達されない代わりに、自分から外に出ることもできません。しかし ECS タスクは ECR からイメージを pull し、Secrets Manager や CloudWatch Logs にも到達する必要があります。そこで、外向きの通信だけを許す NAT Gateway を使います。

    やってみよう（README 記載の演習・課金あり）

    「なぜ private subnet に NAT が要るのか」を、実際に壊して確かめる演習です。network を apply したセッション中に：

    terraform destroy -target=aws_route.private_nat

    private subnet 内のリソースからの outbound（ECR pull など）が失敗することを確認したら、just tf-apply network で元に戻します。

    コードを読む③：SG を「1 ルール = 1 リソース」で書く

    SG のルールは、aws_security_group の中に ingress/egress ブロックとして埋め込む書き方もできますが、この構成では使いません。代わりに aws_vpc_security_group_ingress_rule / ..._egress_rule という、1 ルール = 1 リソースの attachment パターンで書きます。

    設計判断

    ALB → ECS → RDS の SG は、それぞれ「1 つ前からだけ通す」という鎖になっています。ALB は 80/443 をインターネットに開き、ECS は「ALB の SG からの app_port だけ」を受け、RDS は「ECS の SG からの 5432 だけ」を受けます。踏み台（bastion）は ingress を一切持たず、RDS への 5432 は踏み台からの egressとして許可されています（SSM Session Manager は Agent 側から接続しに行く方式のため）。「誰が誰に何を許すか」を、SG の参照関係だけで説明できるのがこのパターンの利点です。

    この層にあるもの・まだ無いもの

    network 層には ALB・ECS タスク・RDS の実体は 1 つもありません。あるのは VPC・subnet・route table と、SG という「箱＋ルール」だけです。実体は、それぞれ app 層（第 5 章）と data 層（第 4 章）で作られ、この層の SG ID を terraform_remote_state 経由で参照してアタッチします。

    運用上の注意

    data 層・app 層が存在する状態で network を先に destroy すると、DependencyViolation で失敗し、しかも NAT Gateway と EIP が壊れずに残って課金が続きます。壊す順序は必ず app → data → network（just down がこの順で実行します）。

    確認クイズ

    ECS タスクの SG に、0.0.0.0/0 への 443 egress ルールが必要な理由はどれでしょう？
    1. ALB からのヘルスチェックを受けるため
    2. Terraform が SG のデフォルト全許可 egress を削除するため、ECR pull や Secrets Manager などへの通信を明示しないと塞がってしまうから
    3. RDS への接続に、この 443 ポートを使うから
    4. インターネットから直接 ECS タスクにアクセスできるようにするため

    AWS の素のデフォルトは全許可 egress ですが、aws_security_group リソースは Terraform 管理下に置いた瞬間にそれを削除します。ECR pull・Secrets Manager 参照・ログ送信は、すべて 443 の HTTPS 通信なので、これが無いとタスクは何も取得できず起動に失敗します。RDS への通信は別ルール（5432）です。

    RDS の SG が、許可する送信元を referenced_security_group_id（ECS の SG）で指定しているのはなぜでしょう？
    1. IP アドレスでの指定は、Terraform の仕様上できないから
    2. ECS タスクの IP は変わりうるが SG の ID は変わらないため、IP レンジでの許可よりメンテナンス不要で安全だから
    3. SG 参照にすると、通信が暗号化されるから
    4. RDS は IP アドレスからの ingress を受け付けない仕様だから

    ECS タスクは awsvpc モードで起動のたびに新しい ENI（と IP）を得ます。IP を毎回 SG に書き足すのは非現実的です。SG 同士の参照なら、「その SG が付いているものから」という条件が、IP に関わらず成り立ちます。

    app 層・data 層が apply 済みの状態で、先に just tf-destroy network を実行するとどうなるでしょう？
    1. network だけが正常に destroy され、他の層は影響を受けない
    2. app 層・data 層のリソースが、network と一緒に自動で destroy される
    3. DependencyViolation で destroy が失敗し、NAT Gateway・EIP が残って課金が続く
    4. plan の段階でエラーになり、destroy 自体が始まらない

    data・app 層が VPC や SG に依存したままなので、AWS 側が VPC の削除を拒否します。正しい順序は app → data → network です。just down はこの順で destroy します。

    NAT Gateway をマルチ AZ で冗長化せず、1 個だけにしているのはなぜでしょう？
    1. NAT Gateway は、そもそも複数作ることができない仕様だから
    2. マルチ AZ にすると、private subnet 間の通信ができなくなるから
    3. コスト優先の学習環境で、NAT の役割を学ぶ目的には 1 個で十分という判断だから
    4. 2 つ目の NAT Gateway には、追加の Elastic IP の割り当てができないから

    本来はAZごとにNAT Gatewayを置くのが定石ですが、この構成はコストを最優先しています。NAT Gateway 1 個で $0.062/h、EIP で $0.005/h。2 個にすればこれが単純に倍になります。学習の主目的は「private subnet に NAT がなぜ要るか」の体験なので、冗長化は見送っています。

    SG のルールを、本体に埋め込まず aws_vpc_security_group_ingress_rule のような別リソースで書く利点はどれでしょう？
    1. ルールの評価順序を、明示的に指定できるようになる
    2. 1 ルール = 1 リソースになるので、Terraform の plan で「どのルールが変わったか」がそのまま差分として見える
    3. SG 自体の作成コストが下がる
    4. referenced_security_group_id が使えるのは、この書き方のときだけだから

    本体に埋め込む書き方では、ルールを 1 つ変えただけでも SG 全体が置き換え対象になりがちで、diff も読みにくくなります。attachment パターンなら、変更のあったルールのリソースだけが plan に出ます。

    CHAPTER 4dataセッション毎・ステートフル

    data：唯一ステートフルな層

    RDS PostgreSQL・DB 認証情報のシークレット・SSM 踏み台 EC2。6 層の中で唯一「データが消えると困る」層です（正確には、RDS のデータだけは destroy で消える前提で設計されています）。この章では、terraform_remote_state による層間の配線と、自前でパスワードを管理する判断を読みます。

    この章で読み解くこと

    • terraform_remote_state で、他の層の output を読む方法
    • manage_master_user_password を使わず、自前でシークレットを持つ理由
    • ECS Exec でも VPC エンドポイントでもなく、踏み台 EC2 が必要な理由

    コードを読む①：network 層を参照する

    RDS を置く subnet と SG は、この層では作りません。network 層が作ったものを読みます。

    コードを読む②：RDS 本体

    コードを読む③：パスワードは自分で持つ

    aws_db_instance には manage_master_user_password = true という、AWS 自身に Secrets Manager のシークレットを作らせる近年の定番機能があります。この構成はあえて使いません。

    設計判断

    この構成では、Secrets Manager が 2 本に分かれています（platform の app シークレットと、この db シークレット）。理由は寿命が違うからです。app 用は常時起動層にあり、DB 用は data 層と生死をともにします。実際の SaaS でも、外部 API キーと DB 認証情報は寿命もローテーション頻度も別物です。この構成は、その違いをレイヤー分割でそのまま表現しています。

    コードを読む④：踏み台 EC2 が要る理由

    RDS は private subnet にあり、パブリックアクセスも無効です。ローカルの PC からは直接繋がりません。ではどうやって手元から psql や migration を実行するのでしょうか。

    なぜ ECS Exec でも VPC エンドポイントでもないのか

    AWS-StartPortForwardingSessionToRemoteHost（just db-tunnel の実体）は、SSM 管理下のインスタンスを起点に任意の host:port へフォワードする仕組みです。RDS 自体は SSM 管理ノードになれないので、代わりになるインスタンスが必要です。ECS Exec は interactive command のみに対応し、ポートフォワードには使えません（app 層が実装されても解決しない制約です）。そこで、この専用の踏み台 EC2 を置いています。

    実際の接続手順

    1. ターミナル①just db-tunnel でトンネルを張りっぱなしにする
    2. →
    3. ターミナル②just db-migrate / db-seed / db-check
    実機検証で分かった注意点（README より）

    just db-url が組み立てる接続文字列は sslmode=no-verify を使います。require だと node-postgres の実装上「証明書検証あり」に解決され、RDS の CA バンドルを取得しない方針の下では、トンネル越しに host が localhost になった瞬間に検証が必ず失敗します。no-verify は TLS を必須のまま証明書検証だけ諦める設定です。psql（just db-psql）は逆に PGSSLMODE=require を使います（no-verify を解さないため）。どちらも経路暗号化のみ担保する落とし所です。

    確認クイズ

    manage_master_user_password = true を使わない、いちばんの理由はどれでしょう？
    1. この機能は、PostgreSQL エンジンでは使えないから
    2. この機能を使うと、パスワードのローテーションができなくなるから
    3. AWS が所有するシークレットは Terraform のリソースとして持てず recovery window を制御できないため、destroy のたびに削除待ちのシークレットが残り続ける恐れがあるから
    4. この機能は追加コストがかかり、Secrets Manager を自前で使うより高くつくから

    削除待ちの 7 日間にも課金され、月 10 セッションなら月 $4 — $10 予算の 4 割が「消したつもりのもの」で消えてしまいます。自前で random_password + aws_secretsmanager_secret（recovery_window_in_days = 0）を持てば、destroy で確実かつ即座に消え、状態が決定的になります。

    random_password の override_special に、RDS が禁止する記号（/ @ " スペース）が誤って含まれたまま terraform validate を実行すると、どうなるでしょう？
    1. validate の段階で、構文エラーとして検出される
    2. validate は通り、実際に apply して RDS へ渡ったところで初めて失敗する
    3. plan の段階で、警告が表示される
    4. Terraform が自動的に禁止文字を除去して apply する

    terraform validate は HCL の構文と型をチェックするだけで、生成された文字列が RDS のパスワードポリシーに合うかまでは見ません。「validate が通っても安心できない」という、この構成の教訓の 1 つです。

    踏み台 EC2 に、パブリック IP も SSH 鍵も持たせていません。それでもリモートから RDS へポートフォワードできるのはなぜでしょう？
    1. RDS 自体が SSM 管理ノードとして動作しているから
    2. SSM Session Manager は Agent 側（踏み台）から AWS 管理エンドポイントへアウトバウンドで接続しに行く方式で、インバウンドの穴が不要だから
    3. VPC エンドポイントが、SSH の代わりにトンネルを提供しているから
    4. NAT Gateway が、SSH の代替として機能しているから

    踏み台の SG に ingress ルールは 1 つもありません。egress だけ（443 と、RDS 宛ての 5432）です。SSM Agent が自分から HTTPS で SSM エンドポイントに接続し、そこ経由でセッションが確立されます。RDS 自体は SSM 管理ノードになれないため、踏み台という「起点」が必要です。

    data 層の db.tf（secrets.tf）で、db シークレットの secret_string に ignore_changes を付けていない理由はどれでしょう？
    1. db シークレットは、変更が発生しない設計だから
    2. random_password が Terraform 管理下にあり、Terraform 自身が値の「正」なので、無視すると古い値のまま固定されてしまうから
    3. ignore_changes は、jsonencode を使った secret_string には適用できないから
    4. db シークレットは recovery_window_in_days が 0 なので、無視する必要がないから

    platform 層の app シークレット（第 2 章）は、値を CLI/コンソールから外部投入する運用なので ignore_changes が必要でした。db シークレットは逆に、Terraform（random_password）が値の持ち主です。「誰が値を決めているか」で、扱いが正反対になります。

    network 層を先に destroy してしまった状態で、data 層の terraform plan を実行するとどうなるでしょう？
    1. plan は正常に完了し、apply も問題なく実行できる
    2. network 層が自動的に再作成される
    3. terraform_remote_state が空の output を返し、plan がわかりにくいエラーで落ちる
    4. data 層は network 層に依存していないので、影響を受けない

    terraform_remote_state は「今 tfstate に何が書かれているか」をそのまま返すため、network が destroy 済みだと outputs.private_subnet_ids のような値が存在せず、plan が分かりにくく落ちます。just up が必ず network → data → app → edge の順で、途中を飛ばさず apply するのは、これを避けるためです。

    CHAPTER 5appセッション毎

    app：ALB と ECS Fargate

    ALB・ECS クラスタ・api / worker のタスク定義とサービス、CloudWatch Logs、そして 3 種類の IAM ロール。この層は 3 つの層すべて（network / platform / data）を参照する、配線の集大成です。

    この章で読み解くこと

    • 3 つの terraform_remote_state を束ねて、コンテナの環境変数を組み立てる
    • execution role と task role、なぜ 3 本に分けるか
    • CI（deploy-api）とローカル apply が、同じタスク定義を取り合わないための ignore_changes

    コードを読む①：3 層をまとめて参照する

    コードを読む②：ALB とヘルスチェック

    定番の罠

    apps/api は host: '0.0.0.0' で listen します。localhost 固定だと、ALB のヘルスチェック（コンテナの外から来る）がタスクに届かず、ずっと unhealthy のままになります。README にも「ALB のヘルスチェックが通らない定番の罠」と明記されています。

    コードを読む③：タスク定義 — 3 層の値を環境変数に流し込む

    コードを読む④：3 本の IAM ロール — 誰が何をできるか

    worker のロール（worker_task）はコードの形は同じですが、権限の中身が逆です：dynamodb:PutItem（status 更新用）、s3:PutObject（スナップショット保存）、sqs:ReceiveMessage / DeleteMessage / GetQueueAttributes（キューの消費）。api と worker、どちらのタスクロールも互いの仕事はできません。

    設計判断

    execution role は共用、task role は api/worker で分離。execution role はインフラの都合（コンテナを起動する権限）で、ビジネス権限を含まないため共用しても安全です。task role はアプリのビジネスロジックの権限そのものなので、最小権限の原則に従い、コンテナごとに分けます。「共用してよい権限」と「分けるべき権限」の境界線が、ロールの分割方針そのものになっています。

    コードを読む⑤：CI とローカル apply が取り合わないための ignore_changes

    確認クイズ

    ALB のヘルスチェックに、認証必須の GET /api/items ではなく GET /healthz を使う理由はどれでしょう？
    1. /healthz のほうがレスポンスが軽く、ALB の負荷が下がるから
    2. 認証必須のパスだと ALB は毎回 401 を受け取り、タスクを誤って unhealthy と判定してしまうから
    3. /api/items は POST 専用で、ヘルスチェック（GET）に使えないから
    4. Cognito のトークンが無いと、ALB 自体が起動できないから

    ALB はヘルスチェックのために認証トークンを持ちません。認証必須のエンドポイントを使うと、実際にはアプリが正常でも 401 が返り続け、ターゲットが unhealthy 扱いになってタスクが回転し続けます。/healthz は認証不要なので、この問題を避けられます。

    execution role は api/worker で共用し、task role は分離しています。この違いの根拠はどれでしょう？
    1. execution role のほうが、AWS の仕様上 1 個しか作れないから
    2. execution role はコンテナ起動のためのインフラ都合の権限（ビジネス権限を含まない）で、task role はアプリのビジネスロジックの権限そのものだから
    3. task role は無料だが execution role には課金が発生するため、共用してコストを抑えるため
    4. 共用できるかどうかは、ロール名の命名規則で決まるから

    execution role が持つのは ECR pull・Logs 書き込みという、コンテナを動かすための AWS 管理ポリシーだけです。task role は DynamoDB・SQS・S3・Secrets Manager といった、アプリが実際に触るリソースへの権限で、api と worker では中身がまったく違います（非対称）。だから最小権限のために分離します。

    aws_ecs_service.api から lifecycle { ignore_changes = [task_definition] } を外すと、何が起きるでしょう？
    1. deploy-api workflow が、タスク定義を登録できなくなる
    2. ECS サービスが、常に最新のイメージを自動選択するようになる
    3. deploy-api でデプロイした新しいイメージが、次の terraform apply で state 上の古いタスク定義に巻き戻される
    4. Terraform の plan が、常にエラーで失敗するようになる

    deploy-api workflow は Terraform を介さずに新しいタスク定義リビジョンを登録します。ignore_changes が無いと、Terraform は「state と実際の値が違う」と判断して、次の apply で古い state の値に戻そうとします。これは新しいイメージへのデプロイを台無しにします。

    api task role に dynamodb:DeleteItem を持たせていないのは、どんな考え方によるものでしょう？
    1. DynamoDB の DeleteItem は、IAM ポリシーで制御できない操作だから
    2. api が実際に行う操作（PutItem・GetItem）だけを許可し、使わない操作は持たせない最小権限の原則を、コード上の非対称な権限として表現しているから
    3. DeleteItem は worker のロールにだけ、自動的に付与される仕様だから
    4. items テーブルは論理削除方式で、物理削除自体を行わない設計だから

    api がやることは createItem（insert + put + send）と getItem（select + get）だけです。この構成では items の削除機能自体がなく、DeleteItem を許可する理由がありません。「使わない権限は書かない」という最小権限が、api と worker の非対称なポリシーとしてそのままコードに表れています。

    ECS タスクの CPU アーキテクチャを ARM64 にしています。これに揃える必要があるものはどれでしょう？
    1. RDS のインスタンスクラス
    2. NAT Gateway のスループット
    3. Docker イメージのビルド時のプラットフォーム（ECR に push するイメージのアーキテクチャ）
    4. Cognito App Client の認証フロー

    タスク定義が ARM64 を要求するのに、x86 向けにビルドしたイメージを push すると、Fargate は起動時に exec format error で失敗します。この構成では just image-build が --platform linux/arm64 でビルドし、CI の publish-image も arm ランナーでネイティブビルドすることで、これを避けています（第 7 章で詳しく扱います）。

    CHAPTER 6edge常時起動

    edge：2 オリジンの CloudFront

    フロント配信用の非公開 S3 バケットと、OAC（Origin Access Control）付きの CloudFront。この層は「常時起動なのに、一部だけセッション毎の値に依存する」という、この構成でいちばんトリッキーな配線を持ちます。

    この章で読み解くこと

    • OAC で「CloudFront からしか読めない S3」を作る仕組み
    • dynamic ブロックで、app 層の有無によって構成を切り替える方法
    • /api/* ビヘイビアで、キャッシュとヘッダを正しく素通しする設定
    • terraform_remote_state を使わず、変数で明示的に渡す設計

    コードを読む①：S3 は非公開のまま、CloudFront にだけ読ませる

    コードを読む②：SPA の 2 オリジン distribution

    この distribution は 1 つのリソースですが、役割の違う部分がいくつも詰まっています。1 つの figure に全体を表示し、行をクリックしながら読み進めます。ALB のオリジンと /api/* のビヘイビアは dynamic ブロックで、app 層が存在するときだけ作られます。for_each に「空の値なら空リスト、値があれば 1 要素のリスト」を渡す、Terraform でよく使うイディオムです。

    設計判断：terraform_remote_state を使わない

    edge 層は app 層の ALB の DNS 名を必要としますが、terraform_remote_state では読みません。var.alb_dns_name（デフォルト空文字）として明示的に受け取ります。理由は、destroy 済みの層に対して terraform_remote_state が空の output を返し、plan がわかりにくく落ちる問題を、この層では抱えたくないからです。edge は常時起動なので、app 層が無い状態（セッション終了後）でも plan／apply が成立しなければなりません。「app 層が無いのはエラーではなく通常状態」という前提を、変数のデフォルト値で表現しています。

    コードを読む③：CloudFront の「更新」を速く保つ運用

    CloudFront の distribution 作成・削除は「disable → 伝播待ち → 削除」と進み、時間がかかります（第 0 章）。だから edge 層は作り直さず、既存の distribution を再 apply で更新する運用にしています。

    down の順序が逆向きに重要な理由

    just down は、app を destroy する前に edge を alb_dns_name="" で再 apply します。もしこの順序を守らず、先に app を壊すと、distribution は死んだ ALB の DNS 名を指したまま残り、次のセッションで edge を再 apply するまで /api/* が 502 を返し続けます。実際に M7 では、この「edge 再 apply」の行に cd infra/edge 後の $(cd infra/app && ...) が相対パスとして誤解決され、alb_dns_name が常に空文字になるバグがありました（$(cd ../app && ...) に修正済み）。

    コードを読む④：deploy-web ロール — platform の OIDC provider を data source で引く

    確認クイズ

    custom_error_response の対象を 404 ではなく 403 にしているのはなぜでしょう？
    1. CloudFront は 404 エラーコードを custom_error_response の対象にできない仕様だから
    2. 404 を対象にすると API の本物の 404 応答まで index.html に書き換えられてしまい、OAC 配下の S3 は存在しないオブジェクトに 403 を返すので 403 だけで SPA フォールバックが成立するから
    3. 403 のほうが 404 よりレスポンスが速いから
    4. S3 バケットが非公開なので、404 を返す権限が無いから

    custom_error_response は distribution 全体、つまり /api/* も含めて効きます。404 をルールにすると API の「本当に無い」404 まで巻き込まれます。OAC 配下の非公開 S3 が存在しないオブジェクトに 403 を返す挙動を利用して、S3 側のケースだけを 403 で拾っています。

    /api/* のオリジンリクエストポリシーを、既定の（何も指定しない）ままにすると何が起きるでしょう？
    1. ALB への接続そのものが確立できなくなる
    2. Authorization ヘッダが転送されず、Cognito の JWT が Fastify に届かないため、リクエストがすべて 401 になる
    3. CloudFront のキャッシュが効きすぎて、常に古いレスポンスが返る
    4. ALB のヘルスチェックが失敗し、ターゲットが unhealthy になる

    CloudFront のデフォルトのビヘイビアはヘッダをほとんど転送しません。この構成では AllViewerExceptHostHeader を明示することで Authorization を含むほぼ全ヘッダを素通しし、この問題を避けています。README が「CloudFront を API の前に置くときの最頻出の失敗」と呼ぶ問題です。

    edge 層が ALB の DNS 名を terraform_remote_state ではなく var.alb_dns_name（デフォルト空文字）で受け取る理由はどれでしょう？
    1. edge 層は VPC の外にあるため、remote_state の仕組みを使えないから
    2. app 層が destroy 済み（＝ output が無い）のが edge 層にとって通常の状態であり、remote_state だとその場合に plan が分かりにくく落ちるから
    3. ALB の DNS 名は、apply のたびに値が変わらないため、変数で十分だから
    4. edge 層は app 層より先に apply されるため、参照できる output がまだ存在しないから

    edge は常時起動層なので、app 層が存在しない期間のほうが長いことも普通です。terraform_remote_state は destroy 済みの層に対して空の output を返し plan を壊すので、edge 層はこれを避けて、明示的な変数（デフォルト空文字）で受け取ります。

    just down で、edge の再 apply（alb_dns_name=""）を省略し、いきなり app を destroy するとどうなるでしょう？
    1. edge の distribution が自動的に無効化される
    2. edge 層の terraform state が壊れ、次回 apply が失敗する
    3. distribution が死んだ ALB の DNS 名を指したまま残り、次のセッションで edge を再 apply するまで /api/* が 502 を返し続ける
    4. app の destroy 自体が、依存関係のエラーで失敗する

    edge は app 層に直接依存する Terraform 上の参照を持たないので（変数渡しのため）、app の destroy 自体はエラーになりません。しかし CloudFront の設定は古い ALB の DNS 名を指したまま残るため、フロントから見ると /api/* が壊れたように見えます。これが just down が edge の再 apply を先に行う理由です。

    CloudFront から ALB への接続に origin_protocol_policy = "http-only"（HTTP・平文）を使っても許容できる理由はどれでしょう？
    1. ALB は HTTPS リスナーを持てない仕様だから
    2. ブラウザ〜CloudFront 間は CloudFront が HTTPS を終端しており、CloudFront〜ALB 間は AWS のバックボーン内の通信だから
    3. この構成では、ALB へのリクエストに認証情報を含まないから
    4. CloudFront は HTTP でしかオリジンに接続できない仕様だから

    mixed content 問題（HTTPS のページから HTTP は呼べない）は、あくまでブラウザ側の制約です。CloudFront が終端としてブラウザには常に HTTPS で応答するので、CloudFront から先（ALB まで）は AWS 内部の通信として HTTP で構いません。ALB に ACM 証明書を用意する手間も省けます。

    コードを読む①：up と down は、互いに逆順

    CI/CD の設計：責務を、依存する層のライフサイクルで分ける

    一般的な「push したら ECS にデプロイ」のチュートリアルは、ECS サービスが常時存在する前提で書かれています。この構成では app 層はセッション後に destroy 済みなのが普通なので、そのまま真似すると壊れます。そこで CI（検証）と CD（発行・反映）を分け、CD はさらに「何に依存するか」で 3 つに分けます。

    workflow責務トリガー依存する層
    ci.yml検証のみ（typecheck / test / lint / terraform validate / docker build）。AWS に触らない全ブランチの push（tag は除く）なし
    publish-image.ymlapi/worker イメージを 7 桁 SHA タグで ECR に発行main の CI 成功後platform（常時）
    deploy-web.ymlapps/web を S3 に同期、CloudFront invalidatemain の CI 成功後edge（常時）
    deploy-api.yml発行済みイメージを ECS の api/worker に反映手動（workflow_dispatch）app（セッション毎）
    設計判断：なぜ「発行」と「反映」を分けるか

    publish-image は platform 層（常時存在）にしか依存しないので、main への push で自動にできます。deploy-api は app 層（セッション毎、毎回 destroy）に依存するので、自動にすると「app が無いのに update-service しようとして毎回失敗する」workflow になってしまいます。「イメージを発行する」と「動いている ECS に反映する」は、この構成では別の関心事です。deploy-api を手動にすれば、ロールバックも「発行済みの別の SHA を選んで実行する」だけの、同じ操作で済みます。

    コードを読む③：main だけを CI/CD に晒す多層防御

    第 2 章で、GitHub OIDC の信頼ポリシーが sub を ...:ref:refs/heads/main に固定していることを見ました。ですが、それだけでは塞ぎきれない抜け道が 1 つあります。

    tag push という抜け道

    workflow_run は、起動元の workflow が動いたブランチ名（head_branch）を見て発火します。もし ci.yml が tag の push でも動くなら、「main」という名前の tagを未レビューのコミットに push されると、CI が通った後に workflow_run の branches: [main] フィルタをすり抜けて OIDC ロールに到達できてしまいます。

    この構成は、3 段の多層防御で塞いでいます。

    1. ① ci.ymlon.push.branches: ['**'] — tag の push そのものでは CI を動かさない
    2. →
    3. ② CD 側の ifworkflow_run.event == 'push' かつ head_repository.full_name == github.repository
    4. →
    5. ③ OIDC の sub 条件...:ref:refs/heads/main（第 2 章）
    なぜ 1 つで十分だと考えないのか

    ①だけでも防げますが、CI 側の設定ミス 1 つで③まで全部意味を失うのを避けるため、CD 側にも②の if を重ねています。「push で起動した、このリポジトリ自身の CI だけ」を条件にすることで、fork からの workflow_run 悪用（別リポジトリの CI 成功を騙る）も同時に防ぎます。多層防御は、どれか 1 つが破られても他が残る設計です。

    コードを読む④：ARM64 を、ビルドの入口から揃える

    第 5 章で、ECS タスクが ARM64（Graviton）であることを見ました。イメージ側もこれに揃えないと exec format error になります。

    workflowランナー理由
    ci.yml / publish-image.ymlubuntu-24.04-armECS タスクが ARM64 なので、docker build も発行も arm ランナーでネイティブビルドする
    deploy-web.yml / deploy-api.ymlubuntu-latestアーキテクチャに依存しない作業（S3 同期・ECS API 呼び出し）のため

    ローカルの just image-build も docker build --platform linux/arm64 で固定し、開発機のアーキテクチャに関わらず arm64 のイメージを作ります。CI とローカルの両方で、同じ判断を揃えているのがポイントです。

    値の受け渡し：GitHub Variables 経由、tfstate には触らせない

    CI は tfstate を読みません。各層の値は、あらかじめ just gh-vars で GitHub Actions の Variables（非秘匿）に登録しておきます。

    確認クイズ

    「イメージの発行」（publish-image）は自動、「ECS への反映」（deploy-api）は手動にしています。この違いの根拠はどれでしょう？
    1. ECR への書き込みは無料だが、ECS の更新には追加コストがかかるから
    2. publish-image は常時起動の platform 層にしか依存しないが、deploy-api はセッション毎に destroy される app 層に依存するため、自動化すると app が無い状態で毎回失敗するから
    3. deploy-api のほうが、実行時間が長くタイムアウトしやすいから
    4. ECS へのデプロイは、GitHub Actions の無料枠では実行できないから

    「push したら ECS にデプロイ」という一般的なパターンは、ECS サービスが常時存在する前提です。この構成の app 層はセッション毎に destroy されるので、そのまま自動化すると app が無いときに必ず失敗します。CD の粒度を、依存する層のライフサイクルに合わせて分けています。

    ci.yml が tag の push でも動くように設定されていたら、悪意ある push でどんな抜け道が生まれるでしょう？
    1. ECR に直接、認証なしでイメージを push できてしまう
    2. 「main」という名前の tag を未レビューのコミットに push すると、CI 成功後に workflow_run の branches フィルタをすり抜けて CD ロールに到達しうる
    3. OIDC の sub 条件が、tag の push では検証されなくなる
    4. RDS のマスターパスワードが、tag のログに出力されてしまう

    workflow_run は起動元の head_branch を見ますが、tag push では tag 名がそこに入ります。「main」という名前の tag なら branches: [main] をすり抜けられます。これを防ぐため、ci.yml 自体を tag push で動かさないようにし、CD 側にも event == 'push' と head_repository の一致確認を重ねています。

    just gh-vars が、7 つの値を全部取得してから、まとめて gh variable set するのはなぜでしょう？
    1. GitHub API のレート制限を避けるため
    2. 途中の terraform output が 1 つでも失敗したときに、一部だけ古い値のまま登録される中途半端な状態を避けるため
    3. gh variable set は、複数の値をまとめて渡す形式でしか呼び出せないから
    4. Variables には、一度に 7 個までしか登録できない制限があるから

    set -eu と組み合わせることで、どれか 1 つの output 取得が失敗した時点でスクリプト全体が止まり、1 つも登録されません。行ごとに取得と登録を交互にしていたら、途中で失敗したときに「一部だけ新しい値、残りは古いまま」という状態になりえます。

    x86 の GitHub ランナーで docker build（プラットフォーム指定なし）したイメージを、そのまま ECS（ARM64 タスク定義）で動かすとどうなるでしょう？
    1. ECS が自動的にアーキテクチャを変換して実行する
    2. ECR への push の時点でエラーになる
    3. タスクの起動時に exec format error で失敗する
    4. 動作は遅くなるが、正常に起動する

    ECR は任意のアーキテクチャのイメージを push・保存できるので、push 自体は成功します。しかし ECS の ARM64 タスクが x86 向けバイナリを実行しようとすると、exec format error で起動に失敗します。この構成では arm ランナーでのネイティブビルドと --platform linux/arm64 の明示で、これを防いでいます。

    just leaks が確認する項目に、DynamoDB や SQS が含まれていないのはなぜでしょう？
    1. DynamoDB・SQS には、消し残しという概念自体が存在しないから
    2. これらは常時起動の platform 層にあり、そもそも destroy 対象ではないため、「消し残し」を心配する必要がないから
    3. AWS CLI に、これらのリソースを一覧するコマンドが存在しないから
    4. DynamoDB と SQS は、無料利用枠の対象で課金されないから

    just leaks がチェックしているのは、NAT Gateway・EC2・EIP・ALB・RDS・削除待ちシークレットという、セッション毎に destroy されるはずのものです。DynamoDB や SQS は platform 層にあり、常時存在しているのが正しい状態なので、チェック対象になりません。
