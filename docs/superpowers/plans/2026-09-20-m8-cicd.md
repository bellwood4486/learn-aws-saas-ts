# M8: CI/CD（責務を分けた4 workflow） Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** GitHub Actions で CI（検証）と CD（成果物の発行・反映）を責務ごとに分けた 4 workflow（`ci.yml` / `publish-image.yml` / `deploy-web.yml` / `deploy-api.yml`）を実装する。AWS への認証は GitHub OIDC のみ（アクセスキーなし）とし、workflow ごとに最小権限のロールを assume する。

**Architecture:** CI は AWS に一切触れない検証専用。CD は main の CI 成功を起点に `workflow_run` で連鎖する（`publish-image` は `platform/`、`deploy-web` は `edge/` の常時起動層に依存）。`deploy-api` だけは `app/`（セッション毎に destroy）に依存するため手動実行で、発行済みの SHA タグを選んで ECS の api / worker に反映する。OIDC provider と `github_publish` / `github_deploy_api` ロールは `platform/`、`github_deploy_web` ロールは `edge/` に置く（権限の対象と同じライフサイクルに合わせる）。CI は tfstate に触れないため、各層の値は GitHub Actions の Variables から受け取る。

**Tech Stack:** GitHub Actions / GitHub OIDC / Terraform 1.15.8, AWS provider `~> 6.0` / just / mise / ECR / ECS Fargate / S3 / CloudFront

**Spec:** `docs/superpowers/specs/2026-08-15-aws-saas-backend-design.md`（「CI/CD」節、「M8: CI/CD」節、「検証方法」のM8行、「Terraformのレイヤー分割」表のplatform/edge行、「justfile」節の`ci`グループ）

## Global Constraints

- Terraform リソース名は snake_case・単数形、リソースタイプ名を名前に繰り返さない。`this`/`main` は使わない
- provider の `default_tags` は既存のまま（`Layer = "platform"` / `"edge"`）。AWS provider `~> 6.0`、Terraform `>= 1.15.0`
- **OIDC の信頼ポリシーは 3 ロールとも `sub = repo:<owner>/<repo>:ref:refs/heads/main` と `aud = sts.amazonaws.com` の `StringEquals`。** `<owner>/<repo>` は `var.github_repository`（**デフォルト無し**）で受け、justfile が `origin` の URL から `TF_VAR_github_repository` として導出して渡す。**owner 名をリポジトリ内のファイルに直書きしない**（プライバシー方針）
- ロール名は `${var.project_name}-github-publish` / `-github-deploy-api` / `-github-deploy-web`
- **イメージタグは `git rev-parse --short=7 HEAD`（7 桁の commit SHA）で固定する。** `latest` は使わない。ECR は `IMMUTABLE`
- CI 用の環境変数は `MISE_ENV: ci`（`mise.ci.toml` が `AWS_PROFILE` を unset する）。`mise.toml` の `[env]` は外から渡した値を上書きするため、これが無いと CI の OIDC 認証が `The config profile (personal) could not be found` で落ちる
- GitHub Actions の Variables（非秘匿）: `AWS_ROLE_ARN_PUBLISH` / `AWS_ROLE_ARN_DEPLOY_WEB` / `AWS_ROLE_ARN_DEPLOY_API` / `ECR_REPOSITORY_URL` / `WEB_BUCKET` / `CLOUDFRONT_DISTRIBUTION_ID` / `COGNITO_CLIENT_ID`。**Secrets は使わない**
- 使う Actions は次のメジャータグ（2026-09-20 時点の最新を確認済み）: `actions/checkout@v7` / `jdx/mise-action@v4` / `aws-actions/configure-aws-credentials@v6` / `aws-actions/amazon-ecs-render-task-definition@v1` / `aws-actions/amazon-ecs-deploy-task-definition@v2`
- リージョンは `ap-northeast-1`（`mise.toml` の `AWS_REGION` と同じ）
- `justfile` のレシピ本体には実際のコマンドをそのまま書く（スクリプトに逃がさない）。全レシピに doc コメントと `[group('...')]` を付ける
- lint: Terraform は `just tf-fmt` / `just tf-validate` / `just tf-lint`、workflow は `actionlint`（`just lint` に含まれる）
- コミットメッセージは Conventional Commits（`<type>(<scope>): <日本語の要約>`）、1 コミット = 1 つの論理的変更。**末尾に、実行者に指定された `Co-Authored-By` 行を付ける**
- **実 AWS / GitHub への副作用は、実行前にユーザーの明示的な承認を得る**（`terraform apply`、`just gh-vars`、`git push`、`gh pr create`、`gh workflow run`、課金セッション）。課金が発生するのは Task 10 の `just up` のみ
- PR タイトルは日本語（`feat(ci): ...` のように type/scope は残す）。PR 本文の Test plan は、実行・検証済みの項目だけ `- [x]` にする

**Interfaces:**
- Produces:

**背景（web-build の修正が必要な理由）:** 現状の `web-build` は `pnpm --filter @repo/web build`（= `vite build` のみ）で、`@repo/contracts` の `dist/` を作らない。ローカルでは過去のビルドで `dist/` が残っているため通るが、CI の新しい checkout では `@repo/contracts` が解決できず失敗する。turbo の `build` タスクは `dependsOn: ["^build"]` なので、turbo 経由にすれば依存が先にビルドされる。

- [ ] **Step 4: `web-build` と `web-deploy` を書き換える**

`justfile` の該当箇所を次に置き換える:

```just
# apps/web をビルドする（.env.local の VITE_* を埋め込む。CI では workflow の env で渡す）。
# turbo 経由にして、依存する @repo/contracts の dist を先にビルドさせる
[group('web')]
web-build:
    pnpm exec turbo run build --filter=@repo/web

# ビルド成果物をedge層のS3バケットに同期し、CloudFrontのキャッシュをinvalidateする。
# WEB_BUCKET / CLOUDFRONT_DISTRIBUTION_ID を環境変数で渡すと terraform output を使わない（CI は tfstate に触れないため）
[group('web')]
web-deploy: web-build
    set -eu; \
    bucket="${WEB_BUCKET:-$(cd infra/edge && terraform output -raw web_bucket)}"; \
    distribution_id="${CLOUDFRONT_DISTRIBUTION_ID:-$(cd infra/edge && terraform output -raw cloudfront_distribution_id)}"; \
    aws s3 sync apps/web/dist "s3://$bucket" --delete; \
    aws cloudfront create-invalidation --distribution-id "$distribution_id" --paths '/*'
```

先頭の `set -eu` が無いと、`;` でつないだ途中のコマンド（`terraform output`）が失敗しても最後のコマンドの終了コードで成功扱いになる。CI が失敗を見逃さないよう必須。

- [ ] **Step 5: `image-push` を書き換える**

```just
# commit SHA（7桁）タグで ECR に発行する。同じタグが既にあれば何もしない（ECR は IMMUTABLE なので再 push は失敗する）。
# ECR_REPOSITORY_URL を環境変数で渡すと terraform output を使わない（CI は tfstate に触れないため）
[group('docker')]
image-push:
    set -eu; \
    repo_url="${ECR_REPOSITORY_URL:-$(cd infra/platform && terraform output -raw ecr_repository_url)}"; \
    tag="$(git rev-parse --short=7 HEAD)"; \
    if aws ecr describe-images --repository-name "${repo_url#*/}" --image-ids imageTag="$tag" >/dev/null 2>&1; then \
        echo "skip: $repo_url:$tag は発行済み"; \
    else \
        aws ecr get-login-password | docker login --username AWS --password-stdin "${repo_url%%/*}" && \
        docker tag learn-aws-saas-ts:local "$repo_url:$tag" && \
        docker push "$repo_url:$tag"; \
    fi
```

先頭の `set -eu` が無いと、`;` でつないだ途中のコマンド（`terraform output`）が失敗して `repo_url` が空のまま Docker Hub に login しに行くことになる。CI が失敗を見逃さないよう必須。

- [ ] **Step 3: `iam.tf` を作成する**

`infra/platform/iam.tf`:

```hcl
# GitHub Actions が OIDC でこのアカウントのロールを assume するための ID プロバイダ。
# アカウントに同じ URL のものは 1 つしか作れないため、既に存在する場合は terraform import で取り込む。
# thumbprint は AWS が GitHub の証明書を自動で検証するので指定しない。
resource "aws_iam_openid_connect_provider" "github" {
  url            = "https://token.actions.githubusercontent.com"
  client_id_list = ["sts.amazonaws.com"]
}

# platform 層の 2 ロールに共通の信頼ポリシー。main ブランチで動く workflow だけが assume できる。
# workflow_run / workflow_dispatch のどちらで起動しても、main 上の実行なら sub は同じ形になる。
data "aws_iam_policy_document" "github_trust" {
  statement {
    actions = ["sts:AssumeRoleWithWebIdentity"]

    principals {
      type        = "Federated"
      identifiers = [aws_iam_openid_connect_provider.github.arn]
    }

    condition {
      test     = "StringEquals"
      variable = "token.actions.githubusercontent.com:aud"
      values   = ["sts.amazonaws.com"]
    }

    condition {
      test     = "StringEquals"
      variable = "token.actions.githubusercontent.com:sub"
      values   = ["repo:${var.github_repository}:ref:refs/heads/main"]
    }
  }
}

# --- github_publish: publish-image.yml が ECR にイメージを発行する ---

resource "aws_iam_role" "github_publish" {
  name               = "${var.project_name}-github-publish"
  assume_role_policy = data.aws_iam_policy_document.github_trust.json
}

data "aws_iam_policy_document" "github_publish" {
  # GetAuthorizationToken はリソース指定ができない
  statement {
    sid       = "EcrAuth"
    actions   = ["ecr:GetAuthorizationToken"]
    resources = ["*"]
  }

  # DescribeImages は「同じタグが発行済みなら push をスキップする」ために使う
  statement {
    sid = "EcrPush"
    actions = [
      "ecr:BatchCheckLayerAvailability",
      "ecr:InitiateLayerUpload",
      "ecr:UploadLayerPart",
      "ecr:CompleteLayerUpload",
      "ecr:PutImage",
      "ecr:DescribeImages",
    ]
    resources = [aws_ecr_repository.app.arn]
  }
}

resource "aws_iam_role_policy" "github_publish" {
  name   = "${var.project_name}-github-publish"
  role   = aws_iam_role.github_publish.id
  policy = data.aws_iam_policy_document.github_publish.json
}

# --- github_deploy_api: deploy-api.yml が発行済みイメージを ECS に反映する ---
# app 層（ECS / IAM ロール）はセッション毎に destroy されるため、このロールは常時起動層の platform に置く。

resource "aws_iam_role" "github_deploy_api" {
  name               = "${var.project_name}-github-deploy-api"
  assume_role_policy = data.aws_iam_policy_document.github_trust.json
}

data "aws_iam_policy_document" "github_deploy_api" {
  statement {
    sid       = "EcrCheckImage"
    actions   = ["ecr:DescribeImages"]
    resources = [aws_ecr_repository.app.arn]
  }

  # RegisterTaskDefinition / DescribeTaskDefinition はリソースレベルの権限指定に対応していないため "*"
  statement {
    sid       = "EcsTaskDefinition"
    actions   = ["ecs:DescribeTaskDefinition", "ecs:RegisterTaskDefinition"]
    resources = ["*"]
  }

  statement {
    sid     = "EcsService"
    actions = ["ecs:DescribeServices", "ecs:UpdateService"]
    resources = [
      "arn:aws:ecs:${var.aws_region}:${data.aws_caller_identity.current.account_id}:service/${var.project_name}/${var.project_name}-*",
    ]
  }

  # app 層のロール（-ecs-execution / -api-task / -worker-task）は destroy 済みで存在しない時期があるため、
  # ARN ではなく名前パターンで絞る。ecs-tasks にしか渡せないよう iam:PassedToService で限定する。
  statement {
    sid       = "PassTaskRoles"
    actions   = ["iam:PassRole"]
    resources = ["arn:aws:iam::${data.aws_caller_identity.current.account_id}:role/${var.project_name}-*"]

    condition {
      test     = "StringEquals"
      variable = "iam:PassedToService"
      values   = ["ecs-tasks.amazonaws.com"]
    }
  }
}

resource "aws_iam_role_policy" "github_deploy_api" {
  name   = "${var.project_name}-github-deploy-api"
  role   = aws_iam_role.github_deploy_api.id
  policy = data.aws_iam_policy_document.github_deploy_api.json
}
```

## Task 7: `deploy-api.yml`（発行済みイメージを ECS に反映する手動 workflow）

**Files:**
- Create: `.github/workflows/deploy-api.yml`
- Modify: `infra/app/ecs.tf`（`aws_ecs_service.api` / `aws_ecs_service.worker` の `lifecycle`）

**Interfaces:**
- Consumes: Variables `AWS_ROLE_ARN_DEPLOY_API` / `ECR_REPOSITORY_URL`（Task 4）、ECR のタグ（Task 6 が発行）、ECS クラスタ `learn-aws-saas-ts`・サービス `learn-aws-saas-ts-{api,worker}`・コンテナ名 `api` / `worker`（`infra/app/ecs.tf` の既存の名前）
- Produces: 手動実行の workflow `Deploy api`（入力 `image_tag`）。実行すると api / worker の新しいタスク定義リビジョンが登録され、サービスが更新される

**背景（`ignore_changes` が必要な理由）:** タスク定義は Terraform が所有している。deploy-api が新リビジョンを登録してサービスの `task_definition` を差し替えると、Terraform の state とずれ、次の `terraform apply` が古いリビジョンに戻そうとする。サービスの `task_definition` の差分を無視する。`just up` は `image_tag` を明示して apply するので、新規作成には影響しない。

- [ ] **Step 1: `deploy-api.yml` を作成する**

`.github/workflows/deploy-api.yml`:

```yaml
name: Deploy api

# 発行済み（publish-image 済み）のイメージを、ECS の api / worker に反映する。手動実行専用。
# app 層（ALB / ECS）はセッション毎に destroy されるため、ローカルで just up した後にだけ成功する。
on:
  workflow_dispatch:
    inputs:
      image_tag:
        description: ECR に発行済みの 7 桁 commit SHA（空なら起動した ref の HEAD）
        required: false
        default: ""

permissions:
  contents: read
  id-token: write

env:
  CLUSTER: learn-aws-saas-ts
  ECR_REPOSITORY_URL: ${{ vars.ECR_REPOSITORY_URL }}

jobs:
  deploy:
    runs-on: ubuntu-latest
    # api と worker はイメージを共用するので、両方のサービスを更新する
    strategy:
      fail-fast: false
      matrix:
        service: [api, worker]
    env:
      SERVICE: learn-aws-saas-ts-${{ matrix.service }}
    steps:
      - uses: aws-actions/configure-aws-credentials@v6
        with:
          role-to-assume: ${{ vars.AWS_ROLE_ARN_DEPLOY_API }}
          aws-region: ap-northeast-1

      - name: 反映するイメージタグを決める
        id: tag
        env:
          INPUT_TAG: ${{ inputs.image_tag }}
        run: |
          tag="${INPUT_TAG:-${GITHUB_SHA::7}}"
          if ! [[ "$tag" =~ ^[0-9a-f]{7}$ ]]; then
            echo "::error::image_tag は 7 桁の commit SHA を指定してください: $tag"
            exit 1
          fi
          echo "tag=$tag" >> "$GITHUB_OUTPUT"

      - name: イメージが ECR にあることを確認する
        env:
          TAG: ${{ steps.tag.outputs.tag }}
        run: |
          if ! aws ecr describe-images --repository-name "${ECR_REPOSITORY_URL#*/}" --image-ids imageTag="$TAG" > /dev/null 2>&1; then
            echo "::error::ECR に $TAG がありません。main の publish-image が完了しているか確認してください"
            exit 1
          fi

      - name: サービスが ACTIVE であることを確認し、現行のタスク定義を取得する
        run: |
```

## レビュー後の変更（実装と計画の差分）

最終レビューの指摘を反映して、実装は上のタスクから次の点で変わっている。タスクの記述自体は当時のまま残している。

- **arm ランナーと `--platform`**: ECS タスクが ARM64 なので、`ci.yml` / `publish-image.yml` は `ubuntu-24.04-arm` で動かし、`just image-build` は `docker build --platform linux/arm64` にした（x86 ランナーだと amd64 イメージになり Fargate で `exec format error`）。`deploy-web` / `deploy-api` は `ubuntu-latest` のまま
- **tag の push で CI を動かさない**: `ci.yml` の `on: push` に `branches: ['**']` を足した。tag 名が `main` だと、後続の `workflow_run`（`branches: [main]`）をすり抜けて OIDC ロールに到達できるため
- **`if:` の多層防御**: `publish-image` / `deploy-web` のジョブ条件に `workflow_run.event == 'push'` と `head_repository.full_name == github.repository` を足した
- **`just lint` で Biome を実行**: `turbo run lint` は各パッケージに `lint` スクリプトが無く 0 タスクで終わっていたため、`pnpm exec biome ci .` を直接呼ぶ形にした
- **`github_deploy_api` の権限を ARN 明示に**: `EcsService` は `-api` / `-worker` の 2 サービス、`PassTaskRoles` は `-ecs-execution` / `-api-task` / `-worker-task` の 3 ロール。IAM ポリシーは存在しないロールの ARN も書けるので、名前パターンで絞る理由（destroy 済み対策）は誤りだった。ワイルドカードだと `github_*` ロール自身にもマッチする
- **`just gh-vars` は取得を先に**: 7 値をすべてシェル変数に取得（`set -eu`）してから `gh variable set` を実行する。途中で output が取れなくても空の値を登録しない
- **`github_repository` の検証**: platform / edge の `variable "github_repository"` に `<owner>/<repo>` 形式の `validation` を足した
- **`deploy-api` の main ガード**: 最初のステップで `$GITHUB_REF` が `refs/heads/main` でなければ分かるエラーで止める（OIDC ロールの信頼ポリシーが main のみのため）
- **`TF_VAR_github_repository` の sed**: `s#^.*github.com[:/]##; s#\.git$##` に広げ、ssh:// や認証情報つき https の origin URL でも `<owner>/<repo>` を取り出せるようにした

## 実機で判明した変更（mainでの初回実行）

main での初回実行で、上のタスクとは次の点が変わった。タスクの記述自体は当時のまま残している。

- **`publish-image` / `deploy-web` が `Not authorized to perform sts:AssumeRoleWithWebIdentity` で失敗した**: `aws-actions/configure-aws-credentials` の assume が拒否された
- **原因は OIDC の不変サブジェクト**: リポジトリの OIDC 設定が `use_immutable_subject: true`（GitHub の新しい既定値）で、`sub` は `repo:<owner>@<owner_id>/<repo>@<repo_id>:ref:refs/heads/main` になる。計画は旧形式（`repo:<owner>/<repo>:ref:refs/heads/main`）を前提にしていたので、信頼ポリシーの条件に一致しなかった
- **`var.github_repository` を `var.github_subject_prefix` に置き換えた**: platform / edge の信頼ポリシーは `${var.github_subject_prefix}:ref:refs/heads/main` を条件にする。所有者/リポジトリの ID で固定するので、リネームや同名での作り直しによる乗っ取りも防げる。`validation` は ID 部分を省略可にして、旧形式のリポジトリも受け付ける
- **`TF_VAR_github_repository` の導出をやめた**: 値の取得には管理者権限つきの API 呼び出しが要り、毎回の `just` 起動や CI では使えない。`just gh-subject-prefix` で取得した値を、git 管理外の `.mise.local.toml` に `TF_VAR_github_subject_prefix` として置く運用にした
