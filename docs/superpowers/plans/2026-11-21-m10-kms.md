# M10: KMS（鍵を自分で持つ） Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 顧客管理キー（CMK）を 1 本作り、KMS の使い方を 2 通り実装する。(A) アプリ用 S3 バケットの SSE-KMS（サービス統合）、(B) `items.note` のアプリ側エンベロープ暗号化（`GenerateDataKey` + AES-256-GCM、暗号化コンテキスト付き）。

**Architecture:** 鍵は常時起動の `platform/` に 1 本置き、他層は `terraform_remote_state` の output（鍵 ARN）で参照する。例 A はバケット設定の切り替えと worker の IAM 追加だけ。例 B は `@repo/core` に `kms.ts`（KMS 呼び出し）と `field-cipher.ts`（暗号文の組み立て）を足し、items のドメイン関数に `FieldCipher` を注入する。復号するのは api だけで、worker は暗号文のまま扱う。

**Tech Stack:** Terraform 1.15.8 / AWS provider `~> 6.0`（`aws_kms_key` / `aws_kms_alias`）、`@aws-sdk/client-kms`、`node:crypto`（AES-256-GCM）、Vitest + `aws-sdk-client-mock`、just / mise

**Spec:** `docs/superpowers/specs/2026-08-15-aws-saas-backend-design.md`（「M10: KMS」節、「検証方法」の M10 行、「destroy 運用で必ず踏む罠」6、「Terraform のレイヤー分割」表の platform 行、「明示的にやらないこと」）

## Global Constraints

- Terraform のリソース名は snake_case・単数形、リソースタイプ名を名前に繰り返さない。`this`/`main` は使わない。鍵のリソース名は `app`（`aws_kms_key.app` / `aws_kms_alias.app`）
- provider の `default_tags` は既存のまま。AWS provider `~> 6.0`、Terraform `>= 1.15.0`、リージョン `ap-northeast-1`、`project_name` 既定値 `learn-aws-saas-ts`
- 鍵: `deletion_window_in_days = 7`、`enable_key_rotation = true`、`rotation_period_in_days = 365`、alias は `alias/${var.project_name}-app`。**鍵は 1 本だけ**（用途ごとに増やさない）
- 鍵ポリシーは **アカウント root への `kms:*` 委譲 1 文だけ**。`prevent_destroy` は付けない（`platform` の他リソースの流儀に合わせる）
- **IAM ポリシーの `resources` に alias ARN を書かない。必ず鍵 ARN**（`aws_kms_key.app.arn` / `outputs.app_kms_key_arn`）
- 例 A の `Condition`: `kms:ViaService = s3.${var.aws_region}.amazonaws.com`（`StringEquals`）。例 B の `Condition`: `kms:EncryptionContext:table = items`（`StringEquals`）
- 暗号文の形式: `v1.<base64url(暗号化データキー)>.<base64url(iv 12 バイト)>.<base64url(暗号文)>.<base64url(tag 16 バイト)>`。アルゴリズムは `aes-256-gcm`、データキーは `KeySpec: 'AES_256'`
- 暗号化コンテキスト: `{ table: 'items', column: 'note', rowId: <行の uuid> }`
- `@aws-sdk/client-kms` は他の `@aws-sdk/*` と同じ `^3.1110.0`。import は拡張子付き（`'./kms.ts'`）。型は `import type`。Biome（`just lint`）と `just typecheck` / `just test` が緑
- テストは AWS に繋がない（`aws-sdk-client-mock`、フェイク）。`s3.test.ts` と同じ書き方
- `justfile` を触る場合は全レシピに doc コメントと `[group('...')]` を付ける（この計画では触らない見込み）
- コミットメッセージは Conventional Commits（`<type>(<scope>): <日本語の要約>`）、1 コミット = 1 つの論理的変更。**末尾に、実行者に指定された `Co-Authored-By` 行を付ける**
- **実 AWS への副作用は、実行前にユーザーの明示的な承認を得る**（`terraform apply`、`just up`、ECR への `just image-push`、`aws kms disable-key` などの変更系 CLI、課金セッション）
- PR タイトルは日本語（`feat(kms): ...`）。PR 本文の Test plan は、実行・検証済みの項目だけ `- [x]` にする
- シークレット・`.env`・`.mise.local.toml` の中身は読まない・出力しない。`aws kms generate-data-key` の `Plaintext` は画面に出さない（`--query CiphertextBlob` だけ取る）

## Review Focus

spec は「何を作るか」しか言わない。次の入力・状況は、どのタスクのテストも素通りしやすい。

1. **S3 の SSE-KMS に書き込む側へ `kms:GenerateDataKey` を足し忘れる** — Terraform は通り、worker が実行時に AccessDenied になってメッセージが再配送→DLQ へ。→ Task 2 の plan 確認と Task 6 の実験 5-a
2. **IAM の `resources` に alias ARN を書く** — 一致せず AccessDenied。→ Task 2 / 5 の `grep` 確認
3. **暗号化コンテキストの不一致**（別の行の暗号文、コンテキスト無し、`table` が違う）— `InvalidCiphertextException` / AccessDenied。→ Task 3 / 4 のテスト、Task 6 の実験 5-b
4. **ローカルの SSO ロールが鍵に触れない**（鍵ポリシーの root 委譲があっても、ロール側の IAM が `kms:*` を許していなければ拒否）— ローカルの `dev-api` や `getObject` が AccessDenied になる。→ Task 1 の `generate-data-key` 確認
5. **境界値**: 4096 バイト超（日本語 2000 文字）の `note`、空文字の `note`、`note` 無し、暗号文の形式でない値（平文の既存行）、改ざんされた暗号文。→ Task 3 のテスト

- [ ] **Step 1: `items.test.ts` を更新して失敗させる**

  テスト内に `FieldCipher` のフェイクを作る（`encrypt` は `enc(<plaintext>)` を返し、`decrypt` は `enc(...)` を外して返す。**どちらも受け取った `context` を記録する**）。`fakeInsertDb` は insert の `values()` の引数を捕まえられる版にする。既存の `createItem` / `getItem` / `listItems` のテストに `cipher` を渡し、次を足す:
  - `createItem は note を暗号化してから insert し、DB には暗号文が入る`（捕まえた `values` の `note` が `enc(world)`）
  - `createItem は行の uuid をアプリ側で生成して insert に渡し、同じ uuid を暗号化コンテキストの rowId に使う`（`values.id` が uuid 形式で、記録した context が `noteContext(values.id)` と等しい）
  - `createItem の戻り値の note は平文（暗号文ではない）`
  - `createItem は note が無ければ cipher を呼ばず、note は undefined`
  - `createItem は空文字の note も暗号化する`（cipher が呼ばれ、戻り値の note は `''`）
  - `getItem は note を復号して返し、復号には noteContext(row.id) を使う`
  - `getItem は note が null なら cipher を呼ばない`
  - `listItems は行ごとに、その行の id の noteContext で復号する`（2 行で context の rowId がそれぞれ違う）
  - `暗号文の形式でない note を読んだら getItem は例外を投げる`（本物の `createFieldCipher` ではなく、フェイクの `decrypt` が `invalid envelope` を投げる形で、例外が握りつぶされず伝わることを確認）
  - `processItem は暗号文のまま S3 のスナップショットの note に入れ、cipher を使わない`（`ProcessItemDeps` に `cipher` が無いことが型で保証される）

- [ ] **Step 2: 失敗を確認する**

  Run: `pnpm --filter @repo/core exec vitest run src/items.test.ts`
  Expected: FAIL

- [ ] **Step 3: `items.ts` を実装する**

  `createItem`: `const id = randomUUID()`（`node:crypto`）→ note があれば `deps.cipher.encrypt(input.note, noteContext(id))` → `insert(items).values({ id, title, note: 暗号文 })` → 戻り値は `composeItem({ ...row, note: input.note ?? null }, 'pending')`（DB の暗号文ではなく入力の平文を返す）。`getItem` / `listItems`: 行を取ったあと note が非 null なら `cipher.decrypt(row.note, noteContext(row.id))` で置き換えてから `composeItem`。重複する復号処理は 1 つの内部関数にまとめる。`processItem` は触らない

- [ ] **Step 4: api を更新する**
